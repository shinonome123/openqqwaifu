# 新版私聊：经历跟进候选

日期：2026-10-26。接在 [主动联系规则](RUNTIME_V2_CONTACT_POLICY.md) 之后，把未结束经历连接到候选、核对、排期、发送、取消和回执核对。仅用于 `runtime_v2` 名单中的私聊。

这一阶段采用**自动形成候选、人工核对正文和时间、程序执行发送**的方式。经历日期不能证明经历已经结束，程序不猜测“明天面试”的完成状态，也不让模型直接决定什么时候联系用户。初始正文是透明标注的模板；后续已接入可明确请求的 [角色化草稿](RUNTIME_V2_FOLLOWUP_DRAFTS.md)，常见时间表达的提取与人工确认见 [经历时间提取与澄清](RUNTIME_V2_EPISODE_TIMES.md)。

## 使用流程

1. 在「会话记录」的「事实与经历」保存带用户原文的未结束经历，或使用已有的结构化记忆提取功能。事实、已完成/已取消/已撤回的经历不生成候选。
2. 「经历跟进」会出现候选，显示经历版本、来源原文和初稿。此时没有发送时间，不会发送；即使用户已开启主动跟进授权，也不会自动排期。
3. 用户明确允许后，在「主动联系规则」确认时区并打开跟进授权。用户也可使用 `/contact on Asia/Shanghai`。全程仍受暂停、静默和共享频率规则约束。
4. 选择「核对并安排」，检查来源与时机，编辑最终正文，填写本地日期时间和核对依据，确认已获得授权。到期时发送保存的正文，不额外调用模型，也不增加“提醒：”前缀。
5. 可以重新安排尚未发送的有效任务、取消跟进，或忽略整个经历的跟进。来源与操作记录展示登录管理员、核对依据、正文、时间和每次触发对应的发送记录。

“忽略此经历的跟进”会阻止该经历后续修订再次生成候选；“取消跟进”只结束这一候选。一次成功发送/模拟捕获后，不再为同一经历自动形成新的跟进。没有重复周期任务。

## 候选与时效

- 候选只来自有原文依据、来源消息在最近 30 天内的 `episode/open` 记录。来源、私聊、角色和经历版本都固定保存在候选中。
- 每个经历版本最多一个候选，每个私聊最多 20 条非终态候选/任务。发现过程每批最多 32 条，不调用模型，也不消耗联系额度。
- 可安排未来 7 天内的时间，使用此私聊当前已确认的 IANA 时区。绝对时间继续校验 DST 跳过/重复，重复时间要求 `fold=0/1`。
- 发送窗口为执行时刻后的 2 小时。暂停、静默、活跃聊天或限额导致的等待都不延长窗口；超窗过期，停机恢复不把过期积压集中补发。来源超过 30 天也会过期。
- 角色只在确认排期时绑定，保存角色卡版本和绑定代次。候选可显示其他角色的经历，但只能安排当前绑定角色的跟进。

初稿从经历标题形成，例如“之前你提到‘面试安排’，最近怎么样了？如果暂时不想聊，也没关系。”它只是待核对的建议；不能据此判断模型的角色表现，也不能把经历标题当成已经核实的事件结果。

## 联系与取消边界

除了既有联系规则，跟进还有固定的保守限制：

- 每滚动 24 小时最多 **1 次跟进发送尝试**，同时计入共享联系额度。所有角色共用此私聊的限制。明确请求的提醒使用原有独立授权，不受这项额外跟进上限约束。
- 用户最近一次入站后至少等待 **30 分钟**；有尚未处理的用户消息、角色切换或记忆修订时，先处理这些工作。
- 两次跟进尝试后没有新的用户消息，就等待新的互动。以可观察的入站事件判断，不推断已读、不表示用户拒绝交流。新消息解除这个等待条件，但仍需满足其他规则。
- 跟进没有夜间例外。安排到静默时段会被拒绝；规则后来变化时，可以在原窗口内等待静默结束。
- 关闭主动跟进授权会取消尚未发送的跟进；重新开启不会复活这些任务。暂停是暂时等待，恢复后仍检查原窗口和全部条件。

经历被修订时，旧候选/草稿失效，新版本只产生未核对候选；完成、取消或撤回经历会停止跟进。已经发出的旧跟进，在关联经历修订或撤回后也从后续模型上下文中排除，避免旧问题再次带入被纠正的信息。审计记录仍可查看，彻底清理使用会话删除。

新消息到达时，已入队但尚未开始发送的跟进退出队列并等待，保证普通聊天可以继续。调度、准备 Outbox 和 `begin_dispatch` 都会重新检查。最后一次检查、发送状态改变和额度计数处于同一事务。

以 `dispatching` 为发送边界：取消/撤权先提交则阻止发送；发送先开始则仍可能到达，保留 `cancel_requested` 和结果核对。unknown 不自动重发，仍阻塞该会话后续发送。管理员核对重试也必须满足时效与限额；由于本阶段每 24 小时最多尝试一次且窗口为 2 小时，已尝试的跟进通常只能核对已发或放弃，不能立即重试。

## 接口

同步与 aiohttp 服务均要求管理员登录：

```text
GET /api/v2/runtime/followups?conversation_id=...&limit=30&before_id=...
GET /api/v2/runtime/followups?conversation_id=...&candidate_id=...
POST /api/v2/runtime/commands
```

列表返回候选、分页游标、当前规则判断、时区、授权/暂停状态、规则版本、数据代次、运行路径状态和发送模式。详情额外返回来源、最近 100 条相关操作和触发/Outbox 链接。

```json
{
  "action": "followup",
  "operation": "schedule",
  "conversation_id": "私聊QQ号",
  "candidate_id": "候选ID",
  "request_id": "本次操作唯一ID",
  "expected_version": 1,
  "expected_data_generation": 1,
  "expected_policy_version": 2,
  "when": "2026-10-27T15:00",
  "fold": null,
  "text": "上次聊到的面试，最近有什么进展吗？",
  "authorized": true,
  "note": "已核对用户跟进授权、原文、正文和合适的联系时间"
}
```

`schedule` 同时用于明确重新安排，需要候选版本、数据代次和联系规则版本一致。旧表单不能跨时区/规则变更继续提交。`cancel`、`dismiss` 需要候选版本、数据代次和操作授权，不要求规则版本。相同请求 ID、内容和账号幂等返回；更换内容或账号会拒绝。操作身份取自登录会话，正文不能伪造。

## 数据、恢复与范围

运行库追加 **schema 7**：`followup_candidates`、`followup_occurrences`、`followup_requests`；共享的 `contact_attempts.kind` 区分提醒与跟进。按原顺序从 schema 1–6 升级。

现有授权偏好保留，旧的近期未结束经历可以成为未排期候选，升级不会自动替用户安排联系。候选、排期、操作和已准备的 Outbox 持久化，重启不重复发现/入队/生成正文。发生在发送中的重启恢复为 unknown。

会话删除包含全部跟进候选、操作、触发、正文和联系计数。独立删除记录库重放仍先清理派生内容，仅为在途/unknown 保留最小发送元数据。删除后重新开始不会带回旧候选和授权，旧排期请求不能跨数据代次重放。

功能不依赖 `reminders_enabled`，但要求新版私聊路由、账号及跟进授权有效。结构化记忆提取仍是独立的默认关闭选项。角色化跟进生成见后续 schema 8 阶段；schema 9 已加入常见时间表达提取及人工确认；未实现自由对话中的自动澄清确认、无人核对的自动排期、周期跟进或群聊主动聊天。
