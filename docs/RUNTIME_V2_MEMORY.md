## 已实现的闭环

新版私聊能够保存两类记录：`fact`（事实或偏好）和 `episode`（经历或安排）。经历区分进行中/计划、已结束和已取消；事实保持有效状态。两类记录均可人工撤回。

每条记录有机器人账号、私聊对象、角色 ID、私聊作用域、来源事件、原文摘录、版本、状态和时间。模型提取标为 `model_extracted`，管理员操作标为 `admin_confirmed`，二者在控制台明确区分。模型的解释不等于已经核实的事实；原文匹配也只能证明引用了用户消息，不能证明解释正确。

例如用户先说“面试周三”，之后说“改成周四”：

1. 第一条记录引用“面试周三”所在的用户事件。
2. 明确纠正可以对同一记录生成新版本，保留原 ID 和修订链。
3. 后续轮次只召回当前版本，并从模型历史中排除旧来源所在的完整轮次，避免旧回复的转述重新带回过期值。
4. 重启后仍能查到当前版本及旧版本的来源与操作依据；历史窗口为零时，也能通过长期记录召回当前值。

“明天”“周四”等相对时间保留原话和来源接收时间。本批没有时区解析或任务调度，不把这些文字自动转为确定日期，也不因为保存了一条安排就创建提醒。

## 控制台操作

管理员进入「会话记录」后，可以在用户消息下点击“记录事实 / 经历”。填写标题、当前内容、该消息中的逐字原文摘录和记录依据；提交后按会话队列顺序生效。

“事实与经历”面板显示当前记录、来源时间、原文及来源事件 ID。可以查看修订历史、纠正内容、改变经历状态，或撤回记录。操作账号来自已认证的管理员会话，不能通过请求正文伪造。

面板中的角色选择仅用于浏览记忆，不改变会话绑定。不同私聊、不同角色和不同机器人账号的记录不会互相召回。已有稳定身份目录、旧知识库和群聊记忆没有自动导入。

人工操作携带目标版本和唯一请求 ID。重复提交相同请求不会重复写入；并发纠正若基于过期版本，会在会话记录中显示“修订未生效”。提交成功只表示已入队，刷新后核对结果；若前面有发送结果不明的轮次，记忆操作也会等待处理。

撤回让记录及关联的来源轮次退出后续模型上下文，仍保留原消息和修订历史。它不是隐私数据的物理删除，也不撤销已经发送或排在该操作之前的回复。需要清除新版私聊全部内容时，使用后续接入的 [会话删除](RUNTIME_V2_PRIVACY.md)，并核对其数据范围。

## 可选的自动提取

自动提取默认关闭。人工确认的记录无论此开关是否开启，都会参与新版私聊召回。若要试运行自动提取，在配置中启用并重启：

```json
{
  "runtime_v2": {
    "structured_memory_enabled": true
  }
}
```

也可使用 `OPENQQWAIFU_RUNTIME_V2_STRUCTURED_MEMORY_ENABLED=true`。页面显示当前运行实例的开关状态；本轮没有改动用户的 `.env` 或部署配置。

启用后，一次结构化模型调用同时产生 `reply` 和最多三条记忆提案。只有 `reply` 正文会发送到 QQ；不增加第二次记忆提取调用。提供商仍须支持既有的消息角色契约，并遵循 JSON 输出指令。此处采用严格的本地响应校验，没有承诺所有兼容服务都会稳定返回合格 JSON。

模型提案需满足：

- 原文摘录逐字出现在本轮用户的一个文本分段中，不能取自机器人草稿、旧历史、昵称、图片或不存在的来源。
- 修订必须指向本轮实际可见的记忆 ID 与版本；不能跨作用域修订，也不能自行覆盖管理员确认或已经撤回的记录。
- 字段、类型、长度、记录种类与状态符合约束；同一轮不能重复修订同一记录。
- 不能通过提案执行工具、修改角色卡或身份目录、创建提醒或取得发送权限。

JSON 无效、证据不存在或版本校验失败时，此轮明确失败并留下原因，不把原始 JSON 发给用户，也不追加一次模型调用“修复”响应。当前仍依赖模型识别同一事件及真正的纠正；语义误判需要人工核对，尚未完成真实模型的多日体验评估。

管理员确认的记录需要人工修订。即使用户随后纠正，模型也只能在当前回复中优先遵守用户最新表达，并提示人工复核长期记录；不会静默改写人工确认值。

## 提交、恢复与上下文

新增 SQLite schema 3，追加 `memory_records`、`memory_revisions` 和 `turn_memory_snapshots`；schema 1/2 会按顺序升级，已有消息、角色、上下文报告和 Outbox 保留。

人工修订使用 Inbox 控制事件，与消息和角色切换共用会话顺序。模型提案在保存回复草稿的同一事务中写入；任何一条提案失败，整组记忆和该次 Outbox 一并回滚。用户自己的陈述可以独立于发送成功保存，机器人未确认发出的草稿不能成为记忆证据。

轮次创建时固定召回快照，恢复生成时复用。已经保存的草稿在重启后直接继续交付，不重复提取记忆。记录撤回或修订不会被同一个已处理事件的重放重新覆盖。

召回先按账号数据库、私聊、角色和当前有效状态过滤，再以中文字符片段/英文词匹配排序，并参考事实类型、未结束经历及更新时间，最多选六条候选。当前没有向量检索、自动过期或语义去重。

记忆正文进入用户数据层，系统层只包含如何解释证据的规则。预算仍优先保留本轮输入与必要人设：先舍弃语气示例，再移除完整旧历史；仍不足时按排序丢弃完整记忆记录。报告记录实际使用的记忆 ID/版本及被省略的 ID，不保存模型请求全文或记忆正文。

升级到 schema 3 后，回退必须使用支持此版本的代码或事先备份并执行专门迁移；旧版 schema 2 运行程序不能直接打开新库。真实部署前仍需备份和回退演练。

## 管理 API

两个 HTTP 实现均要求管理员登录：

```text
GET /api/v2/runtime/memories?conversation_id=...&character_id=...&limit=30&before_id=...
GET /api/v2/runtime/memories?conversation_id=...&character_id=...&memory_id=...
POST /api/v2/runtime/commands
```

列表使用 `next_before_id` 翻页，`limit` 为 1—100；详情返回当前记录及最近 100 个修订版本。创建示例：

```json
{
  "action": "memory",
  "conversation_id": "私聊QQ号",
  "character_id": "quiet-reader",
  "source_event_id": "该角色处理过的用户消息事件ID",
  "request_id": "此次操作唯一ID",
  "note": "核对依据",
  "change": {
    "op": "create",
    "memory_id": "",
    "expected_version": 0,
    "kind": "episode",
    "title": "面试安排",
    "text": "用户说面试在周三",
    "quote": "面试周三",
    "state": "open"
  }
}
```

修订使用 `op=revise`、已有 `memory_id` 和看到的 `expected_version`；撤回使用 `op=withdraw`、`state=withdrawn`。三种操作都要求来源摘录和人工依据。人工正文可以是核对后的解释，与引用原文不同之处由操作账号和备注说明。
