## 控制台操作

在「会话记录」选择私聊，在“会话数据”中点击“预览删除范围”。预览列出消息与控制事件、历史条目、事实/经历、修订、提醒任务及请求、召回快照、上下文报告、出站消息的数量，并列出在途或结果不明的发送。

输入该私聊对象的完整 ID、勾选范围确认，再确认删除。接口同时校验预览令牌：预览后有新消息或其他影响范围变化，旧预览被拒绝，须刷新后重新核对。此操作只删除当前选择的会话，不按当前浏览角色缩小范围。

删除完成后，内容立即退出查询和生成上下文，旧待发消息与提醒停止执行。会话进入暂停接收状态；此时收到的消息只做忽略确认，不保存正文、不生成回复。带平台 ID 的被忽略入站保留哈希去重标识，后续重放也不会被当作新消息。

如果删除时已经有发送进入 `dispatching` 或 `unknown`，正文仍被清除，只留下用于核对的发送 ID、目标、尝试次数、时间和状态。页面显示“内容已删除 · 发送仍待核对”。不能重试已删除正文，不能把删除等同于 QQ 撤回。

管理员可以根据平台记录确认已交付或放弃草稿。在途操作返回确定结果后，或所有 unknown 已完成核对后，才能选择角色并点击“开始新的会话”。新会话不恢复旧历史、事实或提醒；平台用户标识命名空间也包含新的删除代次，避免复用原代次的标识。

重新开始后的入站必须有平台消息 ID。缺少 ID 时无法区分旧回调与新消息，因此拒绝处理；删除前已知的消息 ID 以及暂停期间已知的消息 ID 会继续去重。若外部服务改变重放消息的 ID，本地无法从未保存的正文判断是否重复。

## 删除范围与保留内容

清除当前运行库内该私聊的消息正文和协议载荷、出站草稿、轮次角色快照、事实与经历、修订原文、来源摘录、提醒和请求账本、召回快照、上下文诊断，以及原操作备注。清理控制台当前会话中的记忆/提醒编辑缓存。

保留的数据仅用于防止复活或确认外部结果：

- 私聊对象 ID、会话删除代次和暂停状态。
- 删除操作的管理员账号、时间、数量、请求标识及摘要。
- 入站/控制事件标识的哈希，以及对应的内部事件 ID 和序号，不保留消息正文。
- 删除时仍在途或结果不明的最小发送记录；之后的核对只保存动作，不保留自由文本备注。

全局角色卡、旧版 JSON/知识库/身份目录、另一发送模式的库、其他会话、既有备份、用户已经保存的导出或页面副本，以及 QQ/模型提供商端的数据不在此接口范围内。删除前已经进入模型或发送器的数据无法从外部收回；尚未结束的调用可能在内存中持有原输入直到返回，其结果不会写回本地或产生新的发送。

这是应用数据清除，不承诺磁盘介质的取证级擦除。SQLite 开启 `secure_delete`，提交后尝试截断 WAL；旧备份、系统快照、正在读取的外部连接和文件系统行为仍需要独立的保留策略。

## 删除代次与并发

运行库升级到 schema 5，为会话增加 `data_generation` 和 `privacy_state`，为 Outbox 增加 `erased`，并保存独立删除记录库的身份。

每轮开始时固定删除代次。读取历史、记录上下文、执行提醒命令和提交回复/记忆提案时重新检查代次。删除与待发消息开始发送都通过同一 SQLite 写事务排序：

1. 删除先提交：旧草稿被清除，`begin_dispatch` 不再允许发送；旧模型返回、记忆提案与诊断写入被丢弃，工作线程继续正常运行。
2. 发送先开始：不能保证撤回，保留最小核对状态。回执只更新交付元数据，不重新创建 assistant 历史或提醒。

删除后即使已经重新开始新会话，旧工作仍携带旧代次，不能提交到新会话。会话序号保持递增，不通过重置编号复用旧位置。操作系统单写入者锁仍负责同一运行库的实例归属。

## 恢复旧备份时的屏障

删除意图先持久提交到独立记录库，然后在主库中应用删除。记录库与主库分别使用 SQLite 事务；没有假设两份文件可以跨库原子提交。

对应文件位于同一数据目录：

```text
runtime-v2.sqlite3             ↔ runtime-v2.privacy.sqlite3
runtime-v2-preview.sqlite3     ↔ runtime-v2-preview.privacy.sqlite3
```

若在记录意图后、清理主库前退出，下次打开主库时先重放删除记录，再允许查询、接收和发送。同一次进程里清理失败则停止相关读写，要求恢复后重启，不能继续暴露事务回滚后的旧内容。

恢复较早的主库备份时，最新删除记录会移除旧备份中的已删除数据。记录还保存删除时未核实的发送 ID；即使备份早于该会话的创建，也会恢复最小核对屏障，不能直接重新发送。已经在旧备份之外核实过的发送可能需要再次人工确认，这是保守恢复行为。

记录库缺失、账号/模式/身份不匹配，或明显落后于主库的删除代次时，运行时拒绝打开。只读 CLI 检查也拒绝读取尚未应用删除记录的旧主库，避免绕过启动恢复流程。主库丢失但记录库仍在时，不会自动退回旧引擎。

**恢复操作必须保留最新的 `.privacy.sqlite3`，不能用旧备份覆盖它。** 本批没有提供自动备份恢复或外部追加式存储服务。如果主库和删除记录库一起被退回同一个旧时间点，单凭这两份旧文件无法证明曾有后续删除；需要部署层保留最新删除记录及自己的备份留存策略。删除记录库因此不能随普通历史过期一起清理。

## 管理接口

同步 HTTP 与 aiohttp 均要求管理员登录：

```text
GET /api/v2/runtime/privacy?conversation_id=...
POST /api/v2/runtime/commands
```

GET 返回当前状态、删除代次、数量、影响范围令牌、未核实发送及最近 30 条不含正文的删除记录。删除请求：

```json
{
  "action": "privacy",
  "operation": "erase",
  "conversation_id": "私聊QQ号",
  "request_id": "本次操作唯一ID",
  "preview_token": "GET返回的preview_token",
  "confirmed": true,
  "confirm_conversation_id": "私聊QQ号"
}
```

同一请求 ID 与相同内容重放只返回当前状态，不再次删除重新开始后产生的新数据。操作账号来自已认证管理员会话，不能由请求正文伪造。

重新开始使用 `operation=resume`，提供 `conversation_id`、看到的 `expected_generation` 和 `character_id`。旧代次请求不能重新开启已经再次删除的会话。已经处于相同代次的正常接收状态时，重复恢复不切换角色。
