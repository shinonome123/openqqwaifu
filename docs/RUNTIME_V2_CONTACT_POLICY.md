# 新版私聊：主动联系规则

日期：2026-10-26。承接 [持久提醒](RUNTIME_V2_REMINDERS.md) 和 [会话删除屏障](RUNTIME_V2_PRIVACY.md)，完成主动行为的第一步：每个私聊的授权、时区、静默时段、频率限制和暂停恢复。仅作用于 `runtime_v2` 名单中的私聊，不控制旧运行路径或群聊。

后续已接入 [经历跟进候选](RUNTIME_V2_FOLLOWUPS.md)，当前运行库为 schema 7：未结束经历形成未排期候选，用户开启授权后，仍需在控制台核对正文和时间才能安排。模型不能直接排期。下文 schema 6 和测试数量是联系规则阶段记录。

## 默认行为

- 主动跟进授权默认关闭。用户明确请求的一次性提醒仍有独立授权，不需要打开主动跟进选项；实例的 `reminders_enabled` 仍需开启。
- 默认静默时段为 **22:00–08:00**，按此私聊已确认的 IANA 时区判断，开始时刻包含、结束时刻不包含。也可改为白天的一段时间，或明确关闭静默。
- 每个私聊默认滚动 **24 小时最多 20 次发送尝试**，每次至少间隔 **1 分钟**。可设上限 1–100 次、间隔 1–1440 分钟。所有角色共享该私聊的额度，普通聊天回复不计入。
- 暂停阻止全部计划联系，**包括明确创建的提醒和夜间例外提醒**。用户发消息后的普通回复仍照常处理。
- 恢复继续检查时间、额度、角色绑定、经历状态与原补发截止时间。已取消、已过期或因绑定/经历失效暂停的提醒不会复活。

频率按实际进入 `dispatching` 的尝试计数，发送成功、明确拒绝、结果不明和管理员批准的重试都计入。扫描到期任务、创建任务或预备草稿不会消耗额度。使用滚动时间窗，切换时区不会重置计数；重启也不会重置。

## 私聊命令

以下命令由程序直接解析，控制操作不经过模型：

```text
/contact status
/contact pause
/contact resume
/contact on Asia/Shanghai
/contact off
/contact timezone America/New_York
/contact quiet 22:00 08:00
/contact quiet off
/contact limit 5 30m
```

`on` 打开已核对经历跟进的授权，不能解除暂停，也不会自动排期候选；`off` 撤销主动跟进授权并取消待发跟进，不会撤销用户已明确请求的提醒。要停止提醒也一起联系，使用 `pause`。已确认时区后可省略 `on` 后面的时区。`resume` 不改变主动跟进授权。

还接受完整匹配的“暂停主动联系”“不要主动联系我”“别主动联系我”，含引用或额外语句时不会猜测执行。未识别的 `/contact` 格式返回帮助。规则变更在成功入站的同一事务中生效，回复仍按会话队列发送；旧命令的回复重试不会再次改变规则。失败命令也保留幂等结果。

回复队列已满时，精确暂停命令仍会保存并执行，只是不再排入确认回复；控制台可以核对状态与操作记录。原有结果不明的发送屏障仍保留。

新会话使用部署者已经确认的 `runtime_v2.reminder_timezone` 作为初始时区，若为空则保持未确认，绝不推断开发电脑的时区。每个会话确认自己的时区后，未显式指定时区的新提醒采用会话时区。

## 提醒如何遵守规则

静默开启时，创建或延期至静默时段的提醒会被拒绝，并要求明确确认单条例外：

```text
/remind 2026-12-01T23:00 Asia/Shanghai allow-quiet | 喝水
/remind postpone 提醒ID +30m allow-quiet
```

`allow-quiet` 只绕过静默时段，不能绕过暂停、频率、角色/经历授权或过期检查。延期必须重新确认例外，不继承原时间的夜间许可。管理页面也提供默认未勾选的独立选项。

静默开启且无例外时，相对时长也需要已确认时区，或在提醒中明确指定时区；以前用于显示相对时长的 UTC 回退不代表用户住在 UTC 时区。静默关闭或单条明确例外时，相对时长仍可使用 UTC 显示。

如果提醒创建后规则发生变化，尚未发送的提醒在原补发窗口内等待。已经入队或准备 Outbox 的提醒会撤销旧触发，回到等待状态并释放会话队列；条件恢复时产生新版本的触发。普通聊天和恢复命令不会被这种等待堵在队首。暂停或静默期间仍检查过期，不延长原截止时间。列表显示等待原因和已知的最早再次检查时间，这不是保证发送的时间。

静默按真实 UTC 时刻转换到当地钟表时间判断；寻找下一开放时间时沿真实分钟推进，覆盖夏令时跳过和重复的小时。绝对提醒的 `fold=0/1` 规则继续保留。

## 发送与恢复边界

调度、预备草稿和 `begin_dispatch` 都检查实时联系规则。最后一次检查、发送状态变更和频率计数在同一 SQLite 事务内完成。

暂停先提交，就阻止尚未开始的发送；发送先进入 `dispatching`，则消息仍可能到达，不能声称已撤回。控制台和命令回复都提示这一边界。未知结果继续需要人工核对，暂停/恢复不会消除屏障。重试还会检查当前联系规则，界面与接口都禁止绕过暂停或限额。

删除会话时，联系规则、操作记录和尝试账本一并清除，删除预览包含对应数量。独立删除记录库重放时也清除这些表，避免恢复旧主库带回旧授权。明确开始新会话后，主动跟进重新默认关闭；旧工作不能回写，旧管理员授权请求不能跨删除代次重放。

## 控制台与接口

管理员打开「会话记录」并选择私聊，可以看到「主动联系规则」面板：当前授权、静默时段、额度、阻止原因、立即暂停/恢复、设置编辑和最近 30 条变更记录。

常规编辑需要确认用户授权、填写依据，并检查规则版本。紧急暂停允许规则版本过旧，仍要求数据代次一致，防止旧页面影响删除后新建的会话。操作身份来自登录会话，请求正文不能伪造。

同步和 aiohttp 两种服务器提供相同的管理员接口：

```text
GET /api/v2/runtime/contact-policy?conversation_id=...
POST /api/v2/runtime/commands
```

GET 返回 `policy`、`data_generation`、`attempts_24h`、`remaining_24h`、提醒/主动跟进的规则判断、`followups_implemented=true`、`followup_mode=reviewed_candidates` 和变更记录。规则判断只表示此刻的联系边界，不替代单个任务的完整有效性检查。

```json
{
  "action": "contact_policy",
  "operation": "update",
  "conversation_id": "私聊QQ号",
  "request_id": "本次操作唯一ID",
  "expected_version": 1,
  "expected_data_generation": 1,
  "authorized": true,
  "note": "用户明确确认时区和联系频率",
  "changes": {
    "proactive_enabled": false,
    "timezone": "Asia/Shanghai",
    "quiet_enabled": true,
    "quiet_start": "22:00",
    "quiet_end": "08:00",
    "daily_limit": 5,
    "min_interval_minutes": 30
  }
}
```

暂停/恢复使用 `operation=pause/resume`，省略 `changes` 或使用空对象；不能通过任意字段修改暂停状态。相同请求 ID、内容和操作账号幂等返回；不同内容重用 ID 被拒绝。只支持已建立的有效私聊，未登录/非管理员分别返回 401/403，读取未知会话返回 404，无效或冲突的写入返回 409。

## 数据升级与验证

运行库追加 **schema 6**：`contact_policies`、`contact_requests`、`contact_attempts`，以及提醒的 `allow_quiet`、`timezone_confirmed`、`deferred_until` 字段。保留 schema 1–5 原迁移，启动时顺序升级。

已有私聊初始化为主动跟进关闭、静默开启。已有提醒不会自动获得夜间例外，旧发送尝试会导入额度账本。旧 UTC 提醒无法区分显式时区和显示回退，只有部署默认时区也明确为 UTC 时才将旧 UTC 字段标为已确认；其他旧有效 IANA 时区保留为明确时区。静默判断优先采用会话已确认时区；会话和任务均无确认时区时，保守等待确认或重新安排。升级可能让旧夜间任务等待或过期，升级前应核对未完成任务。

代码回退需要兼容 schema 6；恢复时继续遵循最新独立删除记录库的要求。此步骤没有自动迁移旧引擎的聊天/任务，也没有开放多实例发送者。
