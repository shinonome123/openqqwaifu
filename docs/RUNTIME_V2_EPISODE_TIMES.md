# 新版私聊：经历时间提取与澄清

日期：2026-10-26。接在 [角色化跟进草稿](RUNTIME_V2_FOLLOWUP_DRAFTS.md) 之后。新版私聊中的未结束经历可以产生带来源的时间提案；本文介绍管理员核对流程。后续已接入 [私聊中的经历时间确认](RUNTIME_V2_EPISODE_TIME_DIALOGUE.md)，用户也可以直接核对并确认日期、时段或具体钟点。

## 使用流程

入口：**会话记录 → 经历跟进 → 澄清经历时间**。

1. 查看经历的用户原文及时间解释。相对日期以该消息的接收日期、此私聊已配置或确认的 IANA 时区为基准；不采用电脑时区，也不按今天反复重算历史消息的“明天”。
2. 对模糊表达先向用户核对。面板提供建议询问文本和可能的解释；日期输入默认留空，不自动选中某个解释，也不自动把询问发给 QQ 用户。
3. 选择已经核实的精度：只确定日期、日期与时段、确切日期与钟点。可以选用候选，也可以根据澄清结果人工填写。
4. 核对时间确认所依据的用户消息 ID、逐字引文和说明。若用户后来提供了澄清，使用该条消息的事件 ID 和原文；服务端检查它属于当前私聊及角色。
5. 确认后，跟进仍没有自动发送时间。需要主动联系时，另行核对正文、发送时刻和联系授权。

时间确认不依赖主动跟进开关，因为它只是经历资料。发送仍必须满足既有逐私聊授权、静默、额度和排期核对。时间核对不会创建提醒，不表示经历已经发生或完成。

## 本阶段支持范围

提取采用有限规则，不调用模型，也不把模型摘要中的日期当作证据；只检查经历保留的用户逐字引文。

- 支持今天、明天、后天、大后天、昨天、前天，以及 0—31 天后的常见数字表达。
- 支持本/这/上/下/上上/下下周及星期、礼拜的指定星期几。“周三”没有指定周时，列出来源所在周和下一周，保持未确认；不自动跳到未来。
- 支持完整年月日、`YYYY-MM-DD`、`YYYY/MM/DD`；月日缺年时提示核对来源当年或下一年，两个年份都不是默认值。
- 支持凌晨、上午、中午、下午、傍晚、晚上，以及 `HH:MM`、中文钟点、分钟、半点和一刻/三刻等常见表达。“三点”没有时段时保留上午/下午两种解释。
- “明天下午”只表示日期与下午时段，不生成 15:00，也不生成 UTC 时间点。“明天”只表示日期。
- “过几天”“有空”“周末”等模糊表达、不支持的表达、多个日期/钟点/时段、改期或不确定语句都需要核对。时间范围不自动拆成开始/结束，也不推测经历持续时间。
- 未确认会话时区时不换算日期；原文另提时区时提示先核对。日期、钟点及夏令时跳过/重复都校验；重复钟点需明确第一次或第二次，跳过的钟点不能确认。

例如，2026-10-26 在 Asia/Shanghai 接收到“明天下午面试”，提案是 2026-10-27 下午；同一天接收到“周三面试”，提案包括 2026-10-28 和 2026-11-04。到下一天查看时不会把这些解释继续后移。

规则不能证明自然语言语义完全正确。条件、否定、时区旅行和延迟回调尤其需要人工核对；消息接收日不一定等于用户原本说话时的当地日期。管理员确认表示已结合用户来源核实，不是程序独立验证了事实。

## 上下文与更正

未确认的日历候选不会进入模型上下文，仅提供“时间待澄清”的状态和原有经历证据。确认后，日期、精度、时区和确认来源作为 user 数据层中的经历资料进入普通回复与角色化草稿，不提升为系统指令。

上下文报告增加时间记录 ID、版本、状态和确认来源 ID，继续省略私人正文及具体日期。角色规则明确：日期已过不证明经历完成；日期或时段不能补造成钟点；经历时间不是发送时间；用户当前的纠正优先。

时间确认或清除会使相关正在生成/待核对的旧草稿失效。已安排但尚未开始发送的跟进退回未排期待核对状态，撤销旧 Inbox/Outbox；旧排期表单因候选版本变化而拒绝提交。已开始发送的任务仍可能到达，保留取消标记和结果核对，不承诺撤回。

已发出的旧跟进如果早于或同时于时间更正，也会从后续模型历史中排除，避免重新引入旧日期。使用后来的用户消息确认时间时，原始含旧时间的历史轮次同样排除；原文证据和操作审计仍保留。

经历修订或结束使旧版本时间失效；新经历版本重新形成未确认提案。会话时区变化会清除原确认并重新解释来源；改回旧时区不会恢复原确认。确认表单携带经历、时间、数据、规则、角色绑定及会话序号版本；有新消息或正在处理普通会话时必须先处理并刷新。

普通新消息不会自动被认定为某个经历的改期。可以进入既有经历修订流程、由管理员据新来源澄清时间，或使用后续接入的 [私聊时间核对流程](RUNTIME_V2_EPISODE_TIME_DIALOGUE.md) 指定经历、核对复述并明确确认。

## 接口与存储

追加 **schema 9**：`episode_times` 保存每个经历版本的提案和当前确认，`episode_time_requests` 保存幂等请求、登录身份和历次确认审计。升级后按批次补建时间提案，不自动确认、调用模型或安排消息。旧版应用不能直接打开新版运行库。

继续使用已有管理员接口：

```text
GET /api/v2/runtime/followups?conversation_id=...
GET /api/v2/runtime/followups?conversation_id=...&candidate_id=...
POST /api/v2/runtime/commands
```

候选的 `timing` 提供提案、当前确认、版本和来源。详情的 `time_audit` 返回最近 30 条时间操作；响应还提供 `binding_generation`、`next_seq` 供编辑表单使用。同步 HTTP 和 aiohttp 都要求管理员，身份由登录会话提供。

确认请求示例：

```json
{
  "action": "episode_time",
  "operation": "confirm",
  "conversation_id": "私聊QQ号",
  "memory_id": "经历ID",
  "request_id": "本次操作唯一ID",
  "expected_memory_version": 1,
  "expected_timing_version": 1,
  "expected_data_generation": 1,
  "expected_policy_version": 2,
  "expected_binding_generation": 1,
  "expected_next_seq": 3,
  "precision": "period",
  "date": "2026-10-27",
  "period": "afternoon",
  "clock": "",
  "fold": null,
  "confirmation_source_event_id": "确认依据的用户事件ID",
  "confirmation_quote": "明天下午面试",
  "authorized": true,
  "note": "已与用户核对具体日期，目前只确定下午时段"
}
```

`precision` 可取 `date/period/minute`；`period` 可取 `dawn/morning/noon/afternoon/evening/night`。分钟精度使用 `clock="HH:MM"`，必要时指定 `fold=0/1`。日期和时段精度不能夹带具体钟点。经历可以在过去，不沿用“提醒必须在未来”的约束。

`operation="clear"` 清除确认，不需要再次提供日期与来源，但仍需版本、核对依据和明确确认。相同请求 ID、内容和管理员幂等返回；改变内容或身份拒绝。清除后不会把旧自动提案当成已确认值。

会话删除包含时间提案、确认原文和全部时间操作审计。独立删除记录重放会先清理这些内容；恢复旧主库、删除后重开会话或重放旧确认请求都不能恢复旧数据。
